# Pre-hiring canonical Candidate Knowledge architecture and implementation plan

Date: 2026-07-26  
Status: architecture and implementation plan only  
Production deployment: not authorized  
Production data mutation: not authorized  
Role Profiles: explicitly out of scope

## Executive decision

Create one backend-owned, tenant-scoped `CandidateKnowledgeAuthority` that assembles
authorized candidate knowledge from the current source authorities at read time.

The authority must:

- resolve an exact, tenant-scoped candidate reference without inventing identity;
- aggregate all applications already bound to that candidate by existing backend
  authority;
- load the effective current CV, reviewed facts, classifications, identity-review
  state, application history, assessments, interviews, ranking history, screening
  evidence, notes, and governance state;
- label every fact with source, version, authority, and review state;
- apply permissions, module entitlements, held-state rules, privacy restrictions,
  and response-size policy before returning anything;
- expose typed service methods consumed by AI recruiter tools and Ranking;
- use Voyage and pgvector only for discovery and evidence retrieval;
- never use embeddings for identity, merging, lifecycle changes, or final hiring
  decisions.

Do not build a denormalized “complete candidate JSON” as a second truth store.
Existing canonical tables remain authoritative. New storage is limited to
rebuildable search chunks, indexing jobs, and access audit records.

The intended boundary is:

```text
AI recruiter tools           Ranking readers          Unified Candidates
        \                         |                         /
         \                        |                        /
          +---------- CandidateKnowledgeAuthority -------+
                              |
                 authorization + evidence policy
                              |
       +----------------------+----------------------+
       |          |           |          |           |
    identity   CV/facts   classification apps     assessments/
    authority  authority    authority    history   interviews/ranks
```

## Why this shape

The current recruiter is application-centric and incomplete:

- `rank_candidates` reads applications, candidates, and one application-level
  `semantic_documents` row;
- broad retrieval is bounded before scoring and excludes held Talent Pool rows;
- `candidate_cv_evaluation` reads at most 6,000 characters from the application
  semantic document;
- the live action-registry rank path omits the required `role_profile` argument;
- the same rank loop references `screening` before assigning it;
- the active registry does not register the existing legacy
  `compare_candidates` implementation;
- canonical CV versions, facts, classification, identity review, full history,
  assessments, interviews, and stored rank evaluations are not assembled by one
  reader;
- current tool admission permits legacy empty-permission behavior for read tools.

Adding more joins directly to those executors would create another fragile
application-specific query. A shared authority gives the AI recruiter, Ranking,
dashboard, and future channels one contract while preserving each source table's
ownership.

## Goals

1. Make every authorized candidate knowledge family retrievable through one
   backend contract.
2. Keep tenant isolation and evidence authority explicit in every read.
3. Allow held `needs_role` and `import_review` candidates to be discovered and
   read without making them actionable.
4. Give Ranking the same reviewed evidence that the recruiter can explain.
5. Replace whole-document truncation with version-pinned chunk retrieval.
6. Make missing, stale, invalidated, restricted, and not-yet-indexed evidence
   visible as coverage states rather than silent absence.
7. Preserve existing lifecycle, communication, assessment, interview, and job
   ranking authorities.
8. Remain channel-neutral: email, WhatsApp, and manual upload provenance may
   differ, but their canonical evidence is read through the same interfaces.

## Non-goals

- No production deploy, production schema change, backfill, or data correction.
- No Role Profile entity, ranking, API, UI, or migration.
- No cross-channel pipeline convergence implementation in this work.
- No candidate merge, duplicate cleanup, or Person Registry migration.
- No automatic admission of held candidates to Jobs.
- No change to `intake_admit`, communication gates, or lifecycle predicates.
- No final hiring recommendation generated by Candidate Knowledge.
- No raw unrestricted SQL or database browsing tool for the model.
- No embedding-based identity resolution.
- No re-OCR or extraction triggered by a read request.

## Hard architecture rules

### One read authority, multiple source authorities

`CandidateKnowledgeAuthority` is an assembler and policy boundary. It does not
become the owner of CV facts, classifications, assessments, interviews, or
rankings.

Each source reader must return typed evidence with:

- `source_kind`;
- `source_record_id`;
- `company_code`;
- `app_key` where applicable;
- `document_version_id` and extraction version where applicable;
- `authority_level`;
- `review_state`;
- `observed_at`;
- `valid_from` or `created_at`;
- invalidation or supersession state;
- an evidence reference that can be logged without copying all content.

### Effective values are domain-specific

There is no universal “latest JSON wins” rule.

- Identity: exact normalized, tenant-scoped, confirmed phone/email keys are
  strong. Names are display and review evidence only.
- CV facts: effective HR review events override the pinned extraction snapshot
  for the reviewed fact path.
- Classification: HR-confirmed labels remain distinct from active AI
  suggestions; invalidated runs are excluded.
- Screening: explicit candidate replies are candidate claims. CV-prefill remains
  extracted evidence and must not be presented as a direct answer.
- Assessments: immutable completed score/report versions are authoritative for
  that attempt. Pending or cancelled attempts are state, not negative evidence.
- Interviews: stored status, human notes, transcript, and AI summary remain
  separately labeled.
- Ranking: a score is valid only for its recorded job/criteria/evidence context.
  It is not a general candidate quality score.
- Notes: each note retains its owning workflow, author, visibility, and time.

### Record state is one policy with domain-specific decisions

The checkout currently duplicates held-state constants and does not give
`review_pending` the same meaning everywhere:

- communication and production-search predicates hold `needs_role`,
  `import_review`, and `import_archived`;
- inbound identity and retention logic also treats `review_pending` as held;
- governance adds independent archived, restricted, legal-hold, and deletion
  states.

Do not copy one of those sets into Candidate Knowledge or blindly force every
domain to use one boolean. Add a shared `CandidateRecordStatePolicy` that accepts
the canonical application and governance state and returns named decisions:

- `intake_hold_state`;
- `communication_allowed`;
- `lifecycle_mutation_allowed`;
- `job_ranking_eligible`;
- `talent_pool_search_eligible`;
- `retention_blocked`;
- `read_projection`;
- reason codes and policy version.

Existing authorities remain the execution gates. The shared policy must encode
and test intentional differences so duplicated constants cannot drift silently.

### Retrieval completeness is not prompt size

“All authorized knowledge is retrievable” does not mean “put all rows and the
entire CV into one model prompt.”

The internal authority can assemble a complete typed record. The model-facing
presenter selects relevant sections and CV chunks under a budget, returns
coverage metadata, and supports follow-up pagination. Raw JSON blobs are never
passed through wholesale.

### Reads must be fail-closed

Every request requires:

- non-empty `company_code`;
- active human or service actor identity;
- `permission_authority=backend_current`;
- matching permission subject user and company;
- explicit `prehire.read`;
- module entitlement for module-owned evidence;
- record-level governance evaluation.

An empty or untrusted permission list is denial, including read tools. The new
authority must not inherit the tool orchestrator's legacy empty-permission
compatibility.

## Candidate reference and identity boundary

### Phase-1 reference

Use an opaque application-anchored reference:

```text
candidate_ref = "app:" + app_key
```

The referenced application is only an anchor. After tenant-scoped resolution,
the authority may aggregate other applications that are already bound to the
same existing candidate key within that tenant.

This is deliberate:

- the current candidate table is keyed by phone rather than a tenant-scoped
  person UUID;
- manual imports may use surrogate `imp-...` keys;
- cross-channel duplicates are not safely resolved today;
- introducing a new person identifier would silently begin the deferred Person
  Registry problem.

Phase 1 therefore does not claim that two candidate rows with similar names are
one person. A manual surrogate and a WhatsApp candidate remain separate until a
governed identity process explicitly links them.

### Resolution rules

1. Exact `app_key` resolution is preferred.
2. Exact normalized, confirmed email or phone may resolve through existing
   tenant-scoped identity keys.
3. Name search may return candidates for discovery or an ambiguity response.
4. Name evidence never creates a binding, merge, or automatic canonical
   selection.
5. A shared surname alone never creates even a weak identity match.
6. Open `possible_match` or conflict reviews are surfaced as state, not resolved
   by this service.
7. Embeddings are forbidden in this resolver.

The unresolved GCC name-matching defect should be fixed and regression-tested as
an independent prerequisite before any wider intake enablement. Candidate
Knowledge must not reproduce that matcher.

## Canonical knowledge contract

The internal `CandidateKnowledgeRecord` is a typed object, not a database table.
Its top-level shape should be versioned as `candidate-knowledge-v1`.

```json
{
  "schema": "candidate-knowledge-v1",
  "candidate_ref": "app:<app_key>",
  "company_code": "<tenant>",
  "as_of": "<timestamp>",
  "knowledge_version": "<stable input digest>",
  "subject": {},
  "governance": {},
  "identity_state": {},
  "canonical_cv": {},
  "effective_facts": {},
  "classifications": {},
  "applications": [],
  "screening_evidence": [],
  "assessments": [],
  "interviews": [],
  "ranking_evaluations": [],
  "notes": [],
  "evidence_manifest": [],
  "coverage": {},
  "actionability": {}
}
```

### `subject`

Contains display-safe candidate identity:

- display name;
- grounded contact presence;
- contact values only when the projection policy permits them;
- internal canonical candidate key only inside the service, never in the model
  result;
- source and review state for each displayed contact;
- known language/locale preferences when grounded.

Surrogate import phone values must never be returned as contact information.

### `governance`

Loads `candidate_record_governance` for every aggregated application and computes
the strictest effective state:

- normal;
- archived;
- restricted;
- legal hold;
- deletion requested/in progress/completed;
- retention state;
- owner or intake tag where authorized.

Restricted and deletion states can suppress sections or the entire record.
Legal hold affects retention and deletion, not permission by itself.

### `identity_state`

Returns a safe summary:

- `resolved`;
- `open_review`;
- `conflict`;
- `provisional`;
- `not_governed_by_current_identity_authority`;
- latest policy version and resolution reference;
- strong-key types used, without exposing unrelated candidate identities.

Detailed possible-match candidates and review notes require `candidate.manage`.
The model normally receives only the state and a warning that identity is
unresolved.

### `canonical_cv`

Uses:

- `candidate_documents` for document metadata and current-document ownership;
- `candidate_cv_text_versions` for immutable normalized text;
- current/superseded/invalidated markers;
- extraction method, content hash, document version, and provenance.

Default selection is the current valid version for the anchored application.
Historical versions are metadata-only unless explicitly requested and
authorized. A conflicting-current state produces coverage `conflict` and no
silent selection.

### `effective_facts`

Uses the current valid `application_cv_fact_snapshots` record and applies
`candidate_fact_review_events` through the existing effective-fact projection.

It preserves:

- extraction snapshot;
- effective values;
- HR-reviewed paths;
- rejected paths;
- fact schema and extractor version;
- evidence spans or references;
- confidence and completeness;
- the policy “not extracted is unknown, never negative evidence.”

### `classifications`

Uses:

- latest eligible, non-invalidated `candidate_classification_runs`;
- active `candidate_classification_suggestions`;
- `candidate_classification_review_events`;
- taxonomy labels and versions;
- the existing `effective_classification` separation.

The response keeps `hr_confirmed` and `ai_suggested` arrays separate. Suggested
roles, seniority, career functions, skills, and industries remain advisory.

### `applications`

Returns all tenant-scoped applications already bound to the existing candidate
key, newest first, with pagination:

- app key;
- position code/title;
- held/live/finalized state;
- lifecycle status and dates;
- source/provenance;
- current application flags;
- relevant lifecycle events;
- whether communication, lifecycle mutation, assessment, interview, and job
  ranking are permitted.

The authority must not deduplicate by candidate name. Existing same-candidate
aggregation is based on backend binding, not text similarity.

### `screening_evidence`

Normalizes current WhatsApp screening JSON into typed evidence without rewriting
the source:

- question key and prompt;
- value;
- source `candidate_reply`, `cv_prefill`, or other explicit source;
- captured timestamp;
- correction state;
- confidence, parser/model, and reply evidence reference;
- application and conversation provenance.

Candidate replies may be authoritative for stated preferences such as salary,
availability, and visa status at the time of the reply. They are not CV facts
and may become stale. `cv_prefill` is never relabeled as a candidate reply.

### `assessments`

Loads all tenant/application-matched attempts, with module entitlement:

- battery and immutable content version;
- attempt state;
- completed score, band, and section scores;
- report summary;
- review status;
- timestamps;
- cancellation/expiration state.

Assessment item answers and unrestricted report payloads should not be returned
to the AI by default. The presenter emits the approved summary fields and source
references.

### `interviews`

Loads all canonical interviews and relevant events:

- type, schedule, and status;
- feedback status;
- human notes;
- transcript availability;
- AI summary labeled as AI-generated;
- consent state;
- source and timestamps.

Calendar links, tokens, delivery payloads, and candidate-facing message bodies
are excluded from the model projection unless a separate operational tool needs
them.

### `ranking_evaluations`

Loads stored rank evaluations and, where applicable, canonical job-ranking run
items:

- score and scale;
- breakdown;
- evidence;
- job/position context;
- criteria or role-profile key already recorded by the existing Job Ranking
  authority;
- model and deterministic scorer versions;
- evidence digest;
- stale/current state;
- created time.

This plan does not create Role Profiles. Existing stored `role_profile_key`
fields are read as historical ranking context only.

### `notes`

Phase 1 federates notes from owned workflows:

- application notes;
- screening notes;
- interview human notes;
- assessment review notes;
- identity review notes when permitted;
- fact/classification review notes.

Each item includes source, author, timestamp, application, visibility, and
authority. The service must not claim a complete general HR notes history because
the repository has no single canonical freeform notes authority.

### `evidence_manifest`

Every user-visible assertion references an entry with:

- stable evidence ID;
- source family and record ID;
- application;
- document/extraction/taxonomy/ranking version as applicable;
- authority level;
- review state;
- timestamp;
- content hash or evidence digest where available.

### `coverage`

Coverage is returned per section with one of:

- `available`;
- `partial`;
- `not_recorded`;
- `not_extracted`;
- `not_indexed`;
- `not_authorized`;
- `module_disabled`;
- `restricted`;
- `stale`;
- `invalidated`;
- `conflict`;
- `source_pipeline_incomplete`.

This is essential while email, WhatsApp, and manual upload remain inconsistent.
The authority must disclose incomplete channel processing rather than presenting
missing canonical versions as candidate weakness.

### `actionability`

Actionability is computed from existing backend gates, not inferred by the
model:

```json
{
  "readable": true,
  "contact_allowed": false,
  "lifecycle_mutation_allowed": false,
  "job_ranking_allowed": false,
  "held_state": "needs_role",
  "reason_codes": ["held_intake_application"]
}
```

## Repository completeness prerequisite

The local checkout does not contain ordinary runtime modules for several
deployed authorities, including `candidate_cv_facts`, `candidate_cv_evidence`,
and `candidate_ranking`; parts of their schema and behavior are represented only
by production tables, operational scripts, and deployment patches.

Do not recreate those contracts from inference inside Candidate Knowledge.
Before implementation:

1. restore or check in the deployed source modules and their idempotent schema
   contracts;
2. capture a read-only schema manifest for the affected tables;
3. pin contract tests for fact/evidence materialization and ranking projection;
4. stop if deployed and checked-in contracts disagree.

Candidate Knowledge may consume a versioned interface implemented by those
modules. It must not become their accidental replacement.

## Source reader design

Implement small read-only adapters behind the authority:

- `CandidateSubjectReader`;
- `CandidateGovernanceReader`;
- `CandidateIdentityStateReader`;
- `CandidateCvReader`;
- `CandidateFactsReader`;
- `CandidateClassificationReader`;
- `CandidateApplicationHistoryReader`;
- `CandidateScreeningReader`;
- `CandidateAssessmentReader`;
- `CandidateInterviewReader`;
- `CandidateRankingReader`;
- `CandidateNotesReader`.

Each adapter:

- accepts an already-authorized tenant and resolved application set;
- includes `company_code` in every SQL query even if an earlier resolver did so;
- never takes raw model-generated SQL or table names;
- returns typed DTOs;
- has deterministic ordering;
- reports coverage independently;
- has unit tests for empty, stale, invalidated, and cross-tenant cases.

`CandidateKnowledgeAuthority.get()` orchestrates the readers in one repeatable-read
transaction where practical. The returned `knowledge_version` is a digest of
the selected source IDs, versions, review-event maxima, and policy version.

## Authorization and projection policy

### Base read

Require all of:

- `pre_hiring` module enabled;
- exact backend-current actor context;
- explicit `prehire.read`;
- same tenant for actor, application, and every source row;
- governance permits read.

### Section policy

- Basic candidate/application/CV/facts/classification: `prehire.read`.
- Assessment summary: assessments module plus `prehire.read`.
- Interview summary: pre-hiring/interview module posture plus `prehire.read`.
- Full contact values: model projection defaults to redacted. An exact
  operational need may expose them only under `candidate.manage`.
- Detailed identity review candidates/notes: `candidate.manage`.
- Human notes: `prehire.read` initially, but preserve visibility metadata and
  prepare for a future dedicated notes permission.
- Raw CV download/preview remains in existing file routes, not this AI tool.

The implementation should centralize this in `CandidateKnowledgePolicy`; source
readers must not each invent permission behavior.

### Model projection

The AI recruiter receives a stricter projection than an authorized dashboard
user:

- no raw JSON;
- no surrogate identifiers;
- no malware/quarantine paths;
- no signed links, tokens, calendar payloads, or internal storage paths;
- no unrelated possible-match identities;
- no contact values unless required by an explicitly authorized operation;
- no entire assessment response set;
- no entire CV by default;
- no hidden prompt or model metadata beyond source/version labels needed for
  evidence.

### Audit

Record one append-only `candidate_knowledge_access_events` row per tool or
Ranking read:

- request ID and trace ID;
- company and actor;
- tool/consumer;
- candidate refs and application refs;
- requested and returned sections;
- policy version;
- retrieval mode;
- evidence IDs/counts, not copied evidence text;
- denied/redacted sections and reason codes;
- duration and result status;
- timestamp.

Never put CV text, contact values, interview transcript, or assessment answers
in the access audit payload.

The existing generic admin audit is secondary and currently fail-open. Initial
model-facing Candidate Knowledge reads must not rely on it as the compliance
record. The dedicated access event should be written transactionally before
evidence is exposed to the model; if that write fails, the model-facing read
fails closed. Domain mutation ledgers remain the source of truth for fact,
identity, classification, and retention changes.

## Governed tool contracts

The tools are thin adapters over the same service. They never receive a database
handle and never choose source authority.

### `search_candidates`

Purpose: tenant-scoped discovery across active applications and the readable
Talent Pool.

Request:

```json
{
  "query": "bilingual payroll specialist with Excel",
  "scope": "talent_pool",
  "filters": {
    "status": [],
    "classification_node_ids": [],
    "skills": [],
    "source_channels": [],
    "include_finalized": false,
    "include_archived": false
  },
  "limit": 20,
  "cursor": null
}
```

Allowed scopes:

- `talent_pool`: `needs_role` and `import_review`; archived only by explicit
  authorized filter;
- `active_applications`: existing production/reviewable live predicates;
- `all_authorized`: union with state labels, never a weakened implicit
  predicate.

Response items contain:

- `candidate_ref`;
- display name;
- anchor application and application count;
- held/live/finalized state;
- high-level effective classifications;
- structured and semantic match reasons;
- version-pinned evidence references/snippets;
- retrieval score labeled as search relevance, never hiring score;
- coverage summary;
- actionability.

Response metadata contains:

- stable next cursor;
- retrieval mode `hybrid`, `lexical_only`, or `structured_only`;
- embedding model/index version when used;
- index freshness and coverage;
- total only when computed accurately;
- no claim that the whole pool was scanned unless it actually was.

Search by name is discovery only. A result's exact `candidate_ref` must be used
for subsequent knowledge retrieval.

### `get_candidate_knowledge`

Purpose: load exact candidate knowledge through the shared authority.

Request:

```json
{
  "candidate_ref": "app:<app_key>",
  "focus_question": "What evidence supports her payroll experience?",
  "sections": [
    "subject",
    "canonical_cv",
    "effective_facts",
    "applications",
    "screening_evidence",
    "assessments",
    "interviews",
    "ranking_evaluations",
    "notes"
  ],
  "application_cursor": null,
  "evidence_cursor": null
}
```

The internal record is complete for requested authorized sections. The model
response includes:

- concise effective facts;
- the most relevant CV chunks and evidence spans;
- current/historical source labels;
- coverage and omitted-section reasons;
- next cursors for additional applications or evidence;
- a knowledge version and `as_of`.

No 6,000-character fixed-prefix behavior remains. A question about older
experience can retrieve a relevant chunk near the end of a long CV.

### `compare_candidates`

Purpose: compare two to five exact candidate refs using the same knowledge
contract.

Request:

```json
{
  "candidate_refs": ["app:<one>", "app:<two>"],
  "question": "Compare their stored payroll and GCC experience",
  "dimensions": ["skills", "employment", "languages", "assessments"],
  "job_context": null
}
```

Rules:

- resolve every ref exactly and authorize each record;
- use one evidence schema and one as-of boundary;
- state missing/unknown rather than infer a gap;
- cite evidence per candidate and dimension;
- do not recommend a “best” candidate without a valid existing Job Ranking
  context;
- when a valid job context is provided, read its canonical stored ranking result
  and criteria version rather than silently rescoring;
- never compare on protected traits;
- never create a lifecycle, communication, ranking, or application side effect.

An arbitrary factual comparison is allowed without a Job or Role Profile. It is
not a hiring score.

### Tool errors

Use stable typed failures:

- `tenant_scope_required`;
- `backend_current_permission_required`;
- `permission_denied`;
- `candidate_not_found`;
- `candidate_ambiguous`;
- `candidate_restricted`;
- `identity_review_open`;
- `section_not_authorized`;
- `module_disabled`;
- `canonical_cv_unavailable`;
- `canonical_version_conflict`;
- `index_not_ready`;
- `retrieval_degraded`;
- `invalid_comparison_context`.

Errors must not leak whether a candidate exists in another tenant.

## Search and CV chunk architecture

### New rebuildable index

Add a `candidate_knowledge_chunks` projection in local/staging implementation:

- `chunk_id` stable UUID or hash;
- `company_code`;
- `candidate_ref` or internal anchor app key;
- `app_key`;
- `document_version_id`;
- `source_kind`;
- `source_record_id`;
- section and ordinal;
- normalized chunk text;
- text hash;
- language;
- character/token offsets;
- provider, model, dimensions, and embedding;
- embedding/index version;
- current, superseded, invalidated, and restricted state;
- metadata with evidence references;
- created and indexed times.

This table is not identity authority and not candidate truth. It can be deleted
and rebuilt from canonical sources.

Do not embed:

- names for identity purposes;
- email addresses;
- phone numbers;
- identity-review alternatives;
- malware/quarantine metadata;
- private internal notes in Phase 1.

### Chunking

Use section-aware chunks:

- preserve employment, education, skill, certification, language, and project
  boundaries when extraction provides them;
- use an initial benchmark range around 800–1,200 tokens with bounded overlap;
- retain offsets into the immutable text version;
- keep short headings with their following content;
- index all valid immutable versions, but mark only the current version eligible
  for default search;
- allow explicit historical retrieval without mixing old and current evidence.

Exact chunk size and overlap are qualification parameters, not production
assumptions.

### Voyage and pgvector

- Pin document and query model names and input types.
- Store provider/model/dimensions on every vector.
- Use a pgvector ANN index for the pinned active model/dimension.
- Support dual-write and dual-query during a future embedding model migration.
- Batch document embeddings in the index worker.
- Cache query embeddings by normalized query, model, tenant-safe policy scope,
  and short TTL where appropriate.
- Treat provider failure as disclosed degradation, not silent equivalent search.

Voyage is permitted for:

- semantic candidate discovery;
- relevant CV chunk retrieval;
- job-to-candidate relevance inside the existing governed Ranking context;
- scalable Talent Pool search.

Voyage is forbidden for:

- identity resolution;
- merge or ownership decisions;
- deciding held admission;
- final hiring decisions;
- overriding exact filters, permissions, governance, or reviewed evidence.

### Hybrid retrieval

Candidate discovery should combine:

1. exact/structured filters;
2. lexical full-text search over current chunks and effective structured facts;
3. vector nearest-neighbor retrieval over current eligible chunks;
4. classification filters with confirmed and AI-suggested authority kept
   separate;
5. candidate-level aggregation so one long CV does not crowd out others.

Use a deterministic fusion method such as reciprocal-rank fusion. Return each
component as a match reason. Semantic similarity is a retrieval signal, not the
final displayed ranking score.

Do not repeat the current fixed “nearest 500 then top 10” contract. Query the
index with stable pagination, oversampling, per-candidate aggregation, and
explicit limits. Benchmark exact values against realistic GCC Talent Pool sizes.

### Freshness and invalidation

Enqueue index work when:

- a canonical CV text version becomes current;
- the current version is superseded or invalidated;
- fact review changes searchable effective facts;
- classification effective labels change;
- governance restricts, archives, deletes, or restores a record;
- an identity correction changes application/document ownership;
- the embedding model or chunker version changes.

The index worker is idempotent on:

```text
company_code
+ app_key
+ document_version_id
+ source_record_id
+ source_content_hash
+ chunker_version
+ embedding_model
+ policy_version
```

Identity correction must first invalidate old-owner chunks, then build new-owner
chunks from the corrected canonical authority. Search must exclude invalidated
chunks immediately even if reindexing is pending.

## Ranking integration

Candidate Knowledge and Ranking share evidence, not side effects.

### Input adapter

Add a pure `RankingEvidenceAdapter` that transforms an authorized
`CandidateKnowledgeRecord` into the fields required by the existing Job Ranking
scorer:

- effective reviewed facts;
- current CV evidence/chunks;
- candidate-reply screening claims;
- assessment summaries;
- interview summaries;
- evidence completeness;
- source/version references.

The adapter must not pass raw application/profile JSON as the primary contract.

### Existing job ranking remains authoritative

- Job criteria and existing job ranking run semantics remain unchanged.
- Held Talent Pool rows remain excluded from job ranking.
- Candidate Knowledge reads do not create ranking evaluations.
- A ranking run pins `knowledge_version`, CV version, fact review state, and
  criteria version.
- A changed input marks a prior evaluation stale; it does not rewrite history.
- Missing extraction or missing classification reduces evidence coverage, not
  candidate merit.

### Current rank defects

Before routing active recruiter ranking through the new authority, fix locally
and regress:

- pass the required `role_profile` argument in the registry executor;
- initialize screening data before using it;
- remove broad exception handling that converts scorer programming errors into
  plausible zero scores;
- stop name-first candidate deduplication;
- disclose fallback mode and actual pool coverage.

These fixes are prerequisites for trustworthy qualification, not authorization
to deploy.

## Held Talent Pool policy

`search_candidates(scope="talent_pool")` is a separate held-aware read scope. Do
not weaken `production_application_predicate`.

For `needs_role` and `import_review`:

- semantic, lexical, fact, and classification discovery is allowed when
  authorized;
- exact candidate knowledge read is allowed;
- communication remains denied;
- lifecycle changes remain denied;
- assessments/interviews remain ineligible unless existing authorities say
  otherwise;
- job ranking remains denied;
- explicit `intake_admit` remains the only bridge to a live Job.

`import_archived`, restricted, deletion-pending, and legal/governance states
follow explicit policy and are not included in normal Talent Pool search.

## Additive local schema

The minimum new storage is:

### `candidate_knowledge_chunks`

Rebuildable, versioned CV/fact search chunks and embeddings.

### `candidate_knowledge_index_jobs`

Idempotent queue with company, source/version key, reason, availability time,
attempts, claim lease, completion, last error, and dead-letter state.

### `candidate_knowledge_access_events`

Append-only, content-free audit of candidate knowledge reads and redactions.

Avoid:

- a `candidate_knowledge_records` JSON table;
- copying all source rows into one materialized blob;
- a new candidate/person UUID in this phase;
- storing model answers as candidate truth;
- using `semantic_documents` application rows as immutable version authority.

The existing application-level `semantic_documents` index remains during
migration. It is removed from recruiter authority only after parity,
backfill/coverage, and rollback qualification.

## Qualification cases

### Identity and tenant safety

- Same surname, different given names, no exact email/phone: never resolve or
  merge.
- Exact normalized email in the same tenant: may resolve under identity
  authority.
- Same email/phone in another tenant: invisible.
- Name-only multiple matches: typed ambiguity.
- Open identity review: state visible; no model resolution.
- Manual surrogate plus real candidate: separate candidate refs.

### Evidence authority

- HR-corrected skill overrides extracted value for the effective path.
- Rejected extracted fact is not presented as current.
- HR-confirmed classification survives AI reclassification.
- Invalidated classification run is excluded.
- Candidate reply and CV-prefill remain distinguishable.
- Missing fact is “not extracted,” not a negative claim.
- AI interview summary never appears as human feedback.

### CV retrieval

- Evidence near the end of a long CV is retrieved by question.
- Old CV chunks do not appear in default current search.
- Historical request can retrieve the old version with a historical label.
- Conflicting current versions fail closed.
- Identity correction removes old-owner search visibility immediately.

### Held-state safety

- `needs_role` appears in Talent Pool search.
- Exact held knowledge read succeeds for `prehire.read`.
- Contact, lifecycle, assessment, interview, and job-ranking operations remain
  blocked according to existing authorities.
- Search or compare creates no application, job binding, rank run, message, or
  lifecycle event.

### Permission and privacy

- Empty permissions deny.
- User-supplied permissions without backend-current authority deny.
- Restricted/deletion records suppress evidence.
- `prehire.read` does not reveal possible-match candidate identities.
- Audit rows contain hashes/IDs, not CV text or contact values.
- Cross-tenant timing and errors do not disclose candidate existence.

### Retrieval quality

- Hybrid search finds structured exact skill matches and semantic paraphrases.
- Lexical-only fallback is labeled.
- Pagination can reach candidates outside the first retrieval page.
- Candidate aggregation prevents one multi-chunk CV from dominating.
- Search score is labeled relevance, not suitability.
- Provider failure does not return a false “whole pool scanned” claim.

### Comparison and Ranking

- Comparison uses the same knowledge version for every candidate where possible.
- Missing evidence is explicit.
- No “best candidate” is produced without valid Job Ranking context.
- Job-context comparison cites stored criteria/run versions.
- Held records remain outside job ranking.
- Ranking source changes stale prior evaluations rather than rewriting them.

## Performance and reliability targets for qualification

Set targets before staging based on measured baseline. At minimum measure:

- p50/p95 exact knowledge read latency by section set;
- p50/p95 search latency at 1k, 10k, and expected upper candidate counts;
- embedding/index queue lag;
- current valid CV version coverage;
- chunk embedding coverage by tenant and model;
- stale/invalidated leakage rate, which must be zero;
- cross-tenant leakage rate, which must be zero;
- retrieval recall on a labeled bilingual EN/AR test set;
- semantic provider degradation rate;
- tool token/output size;
- cost per indexed CV and search query.

Do not set a production service-level claim from synthetic timing alone.

## Observability

Metrics:

- reads/searches/comparisons by tenant and result;
- denied/redacted requests by reason;
- section coverage states;
- search retrieval mode;
- index job latency, retries, and dead letters;
- current CV versions without current chunks;
- current chunks tied to invalidated/restricted sources;
- query embedding failures;
- exact-read and search latency;
- model-facing evidence count and output size.

Alerts:

- any cross-tenant assertion failure;
- any restricted/invalidated chunk returned;
- index lag above approved threshold;
- sudden fallback to lexical-only;
- high canonical-version conflict rate;
- permission-authority failures;
- unexpected mutation count from read-only qualification.

Kill switches independently disable:

- indexing workers;
- semantic query use;
- AI recruiter tools;
- Ranking reader integration.

Disabling semantic retrieval must preserve exact and lexical authorized reads.

## Migration and rollback

Migration is additive:

1. add local schema behind schema flag;
2. build chunks from canonical versions without changing sources;
3. run parity reads;
4. shadow new tools;
5. later route recruiter reads only after approval;
6. later route Ranking evidence reads only after separate approval.

Rollback:

- disable tools flag to restore current recruiter tools;
- disable Ranking reader flag to restore existing Ranking inputs;
- disable index workers while retaining source truth;
- semantic search can fall back to lexical/structured search;
- chunk and access tables are not needed for lifecycle operation;
- no source canonical table is rewritten.

Do not remove `semantic_documents`, profile projections, or legacy executors until
an approved production canary proves parity and rollback.
